## Detailed Findings

### [CRITICAL] agent-loop buildRequest — inherited effort reaching an incompatible model fails the whole turn
- **Category**: Correctness / Availability
- **Paths** (all verified in code):
  1. **Stale `agent-default-model` settings**: blank session → apiproxy `selectionFor().current` (api-proxy.ts:1105) / headless `run()` (bundle/headless/src/index.ts:106-117) seed `installModelSelection` with the settings triple *including* `reasoningEffort`; `model-selection.ts:65-67` applies it verbatim → `prepareCall` throws.
  2. **Same-route capability drift**: a logged explicit effort (`requestProposal` keeps it because `adapterDefaults` is absent) re-applied after the model's declared efforts changed (catalog/profile edit) → `prepareCall` throws. The 17:45 `routeMatches` guard cannot fire: the route did not change.
  3. Any `agent/request` waterfall listener forwarding a stale effort.
- **Why drop-at-the-loop is correct**: every live selection is already validated at `session.selectModel` (api-proxy.ts:2200, covered by api-proxy-models.spec.ts "unsupported" case). The only efforts that can reach `buildRequest` unvalidated are inherited ones (persisted header, saved default, plugin proposal). `resolveCallConfig`'s reject-before-I/O contract for *live* validation is preserved; the loop stops forwarding poisoned inherited values (same principle as the accepted 17:45 route-switch strip).
- **Remediation**: in `buildRequest`, catch `UNSUPPORTED_REASONING_EFFORT` from `prepareCall` when the config carries an effort; strip it, warn once per request, re-prepare. The model's own default then applies.

### [WARNING] api-proxy selectionFor getter re-surfaces adapter-materialized defaults as explicit picks
- **Category**: Correctness / Semantics
- **Description**: api-proxy.ts:1104-1112 copies `logged.config.reasoningEffort` into the selection without consulting `adapterDefaults`. When the logged value was materialized from the model's `defaultEffort` (`adapterDefaults.reasoningEffort === true`), the getter promotes a default to an explicit selection; the next same-route pick (`selectionOf` sameRoute branch) re-sends it as user-chosen, pinning it in the next header. `requestProposal` (agent.ts:55-61) already strips these for the seed — the getter is the unexplained asymmetry.
- **Remediation**: strip adapter-default-marked effort in the getter (mirror `requestProposal`).

### [INFO] Prior fix retained
The 17:45 uncommitted `routeMatches` seed guard and its regression test remain correct and necessary; they are one layer of this fix, not superseded.

### [INFO] selectModel validation is correct as-is
